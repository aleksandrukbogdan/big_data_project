# Сбор IT-тендеров с rostender.info

Забираем открытые тендеры IT-категории и кладём сырые данные в три хранилища. Расписанием занимается Apache Airflow 2.10 в Docker.

## Хранилища

| Куда | Что лежит | Почему так |
|---|---|---|
| MinIO | исходные XML и HTML | файл сохраняется как скачали, по дате и номеру прогона |
| MongoDB, коллекция `ods.tenders` | карточка тендера | поля не всегда одинаковые, дату с HTML часто не достать |
| PostgreSQL, порт 5433 | `ods.tender_locations`, `ods.tender_prices`, `ods.tender_cards`, `ods.tender_industries` | город, регион, НМЦ, статус, процедура, сроки и отрасль удобно выбирать запросом |

У Airflow свой PostgreSQL, только для служебных данных. К тендерам он не относится.

## Процессы

```
rostender.info
    ├─ ods_raw_to_minio             → MinIO
    ├─ ods_tenders_to_mongo         → MongoDB
    └─ ods_geo_prices_to_postgres   → PostgreSQL
```

В каждом процессе три шага: скачать, разобрать, записать.

`ods_raw_to_minio` сохраняет `rss.xml` и `category.html` в бакет `ods-tenders` по пути `raw/dt=дата/run_id=.../`.

`ods_tenders_to_mongo` собирает из ленты и страницы карточки и обновляет документ по id тендера.

`ods_geo_prices_to_postgres` из ленты достаёт «Цена» и «Место поставки», регион берёт из адреса `/region/.../`. Затем открывает карточку каждого IT-тендера и дописывает статус, способ размещения, окно подачи заявок, дату заключения контракта и отрасль. Сумма помечается как `price_kind = nmck`: это начальная цена, не цена контракта. Отраслей у одной закупки бывает несколько, они лежат отдельно в `ods.tender_industries`. Повторный запуск обновляет строку по тому же id.

Повторный запуск не создаёт дубли.

## Как поднять

```bash
docker compose up --build airflow-init
docker compose up -d
```

- Airflow: http://localhost:8080, логин `airflow`, пароль `airflow`. Если список пустой, обнови страницу. Прямые ссылки: `/dags/ods_raw_to_minio/grid`, `/dags/ods_tenders_to_mongo/grid`, `/dags/ods_geo_prices_to_postgres/grid`
- Файлы MinIO: http://localhost:9002. В этой версии MinIO нет своей консоли на порту 9001, порт 9000 — это API, не страница.
- Карточки MongoDB: http://localhost:8081, логин `admin`, пароль `admin`, база `ods`, коллекция `tenders`
- Таблицы PostgreSQL: http://localhost:8082. Система PostgreSQL, сервер `postgres-ods`, пользователь `ods`, пароль `ods`, база `ods`. Адрес http://localhost:5433 в браузере не откроется: это порт базы, не сайт.

Процессы сначала стоят на паузе. Её нужно снять и нажать Trigger.

## Сравнение

Один и тот же набор тендеров записали во все три хранилища и замерили время записи, время поиска по id и объём. Скрипт: `scripts/benchmark_stores.py`. Цифры и картинки: `benchmark_results.md`, папка `figures/`.

Прогон 2 октября 2026, 20:43. Взяты файлы последнего ручного запуска Airflow: 37 карточек, сырые XML и HTML.

| Хранилище | Запись, мс | Поиск по id, мс | Объём |
|---|---:|---:|---:|
| MinIO | 248 | 1.8 | 1.3 МБ, 2 файла |
| MongoDB | 30 | 1.4 | 35 КиБ, в коллекции 56 документов |
| PostgreSQL | 12 | 0.8 | 224 КиБ, в таблицах 76 строк |

В MongoDB и PostgreSQL строк больше, чем 37: там остались и предыдущие запуски. Поиск везде быстрее 2 мс. Запись в MinIO дольше, потому что туда уходит вся страница целиком, около 1.3 МБ. В базы попадает уже разобранный текст, он намного меньше.

| | MinIO | MongoDB | PostgreSQL |
|---|---|---|---|
| Исходный файл целиком | да | нет | нет |
| Жёсткая схема | нет | нет | да |
| Выборка по цене и региону | неудобно | можно, но тяжелее | обычный SQL |

Сырые файлы лучше держать в MinIO: их не нужно заранее разбирать. Город и цену удобнее читать из PostgreSQL. MongoDB имеет смысл, если поля карточки часто меняются. На этих тендерах поля стабильные, поэтому для работы хватает MinIO плюс PostgreSQL. MongoDB оставлен в стенде, чтобы сравнить три разных способа хранения.

## Детальный слой

Сырые таблицы остаются в схеме `ods`. Процесс `dds_it_tenders` собирает схему `dds` в той же базе и идёт пятью шагами: очистка, справочники, медленно меняющееся измерение, факт, агрегаты. Следующий процесс `dq_it_tenders` стартует сам, когда факт записан.

Схема — снежинка в третьей нормальной форме. Город ссылается на регион, факт хранит только ключи и меры, отрасль вынесена в мост, потому что у одной закупки их несколько.

Очистка убирает повтор тендера, схлопывает пробелы в регионе, срезает «г.» у города и не пускает в меру нулевую и пустую цену. Обогащение считает часы приёма заявок и дни до контракта, дописывает русские имена регионов и городов и заполняет календарь без пропусков между крайними датами. Агрегаты: `dds.agg_region_procedure` и `dds.agg_deadline_week`.

Факт `dds.fact_tender` — одна строка на тендер. Меры: НМЦ, длительность приёма, дни до контракта. Измерение тендера хранит историю: пока статус, процедура и ссылка те же, новая версия не открывается.

Для витрин лабы 3 читаются `dds.v_tender` и `dds.v_tender_industry`, не сырые таблицы. В представлении уже есть русское имя региона, признак карточки, неделя окончания приёма и начальная цена. По ним собираются число закупок по регионам, сумма НМЦ по процедуре, динамика по неделям, отрасли и доля закупок без цены.

`dds_it_tenders` ждёт успешного `ods_geo_prices_to_postgres`. Проверка качества пишет итог в `dds.dq_result`. Расхождение числа строк, две открытые версии и битая сумма останавливают процесс. Пустая цена и карточка без НМЦ остаются предупреждением.

## Витрины и показ

Процесс `dm_it_tenders` ждёт детальный слой и пересобирает схему `dm`. Пять витрин отвечают на разные вопросы: где закупки, какая процедура держит сумму, когда заканчивается приём, какие отрасли встречаются, у какой доли карточек указана начальная цена. Сумма по отраслям не считается: одна закупка входит в несколько отраслей, и деньги задвоились бы.

Superset: http://localhost:8088, `admin` / `admin`, дашборд «IT-тендеры». Образ собирается из `superset/`, потому что в официальном нет драйвера PostgreSQL. Столбцы показывают сравнение регионов, процедур и отраслей. Линия показывает волну сроков. Круг показывает долю карточек без начальной цены: частей две, и круг это читается сразу.

OpenMetadata: http://localhost:8585, `admin@open-metadata.org` / `admin`. Скрипт `scripts/publish_lineage.py` проводит линию от сырых таблиц к факту и дальше к витринам. Смотреть её на карточке `dds.fact_tender`, вкладка Lineage. Если том Superset или OpenMetadata пустой:

```bash
python scripts/bootstrap_superset.py
python scripts/publish_lineage.py
```
